## 1. المطلوب (بكلام المستخدم)

> «تعديل على السيستم كله: الفلوس ما يكونش فيها علامة عشرية. الفلوس أرقام صحيحة فقط. أي فلوس في السيستم أرقام صحيحة فقط، مفيش أرقام عشرية. مش عايز كل فلوس تضاف يضاف بعدها نقطة وبعد كده صفرين — عايز ألغي الموضوع ده كله من السيستم كله. احنا مفيش أقل من الجنيه، ما بنتعاملش بأقل من الجنيه، فهي أرقام صحيحة فقط في الفلوس. راجع بقى مكانها فين وهيعملها إزاي، وفي الداتابيز شوف، وثبّت لي إن الفلوس دايمًا أرقامها صحيحة.»

## 2. السياق والأسئلة المحسومة

**ليه محتاجين ده؟**
الورشة ما بتتعاملش بأقل من الجنيه أصلًا. القرار المعماري الأصلي (المبالغ integer بالقروش ×100) اتاخد عشان الدقة المالية، بس نتيجته إن كل رقم في الواجهة بيتكتب `7,000.00` وكل إدخال بيحتاج `.00` — ضوضاء بصرية بلا فايدة فعلية في السياق ده.

**الوضع الحالي بالظبط (جرد كامل):**

| المكان | العدد | التفاصيل |
|---|---|---|
| أعمدة فلوس في الداتابيز | **31 عمود** في 14 جدول | كلها `integer` بالقروش |
| الكاست | **ملف واحد** | `MoneyCast` (scale=100, decimals=2) فوق `ScaledIntegerCast` |
| Form Requests | **18 ملف** | كلها بتاخد نمط التحقق من `MoneyCast::validationPattern()` — **مفيش ولا واحد بيكتب نمطه بنفسه** |
| عرض الفلوس | **ملف واحد فعليًا** | كل عرض بيمر من `MoneyCast::toDisplayString()` / `toDecimalString()` — مفيش أي تنسيق فلوس مكتوب بالإيد في أي مكان |
| حقول إدخال `step="0.01"` | 25 حقل في 19 ملف | منها حقول كميات (`step="0.001"`) **خارج النطاق** |
| ضرب/قسمة فلوس | **3 دوال بس** | `InventoryService::cost()` · `InventoryService::unitPriceOf()` · `PartnerService::shareOf()` |

**الخلاصة المعمارية:** المشروع منضبط جدًا في النقطة دي — كل الفلوس بتدخل وتخرج من **مكان واحد** (`ScaledIntegerCast`). يعني التغيير مركزي مش منتشر.

**حالة البيانات الحالية (اتفحصت فعليًا على `database/database.sqlite`):**

```
القيم المالية المخزّنة: 39 قيمة — منها 0 فيها كسور قروش
```

**كل قيمة مالية موجودة دلوقتي هي مضاعف صحيح لـ100 قرش.** يعني الترحيل (÷100) **بلا أي خسارة ولا تقريب على البيانات الحالية**.

**أسئلة اتسألت واتحسمت قبل التنفيذ:**

| السؤال | الإجابة المعتمدة | مين حسمها |
|---|---|---|
| سعر وحدة الخامة (`unit_price`) — فلوس ولا معدّل؟ | **فلوس: رقم صحيح زي أي مبلغ.** التنازل مقبول: شراء 3 بـ100 يتكتب 33 أو 34 | المستخدم |
| نسب الشركاء (33.33%) تتأثر؟ | **لأ.** النسبة مش فلوس — تفضل بخانتين عشريتين زي ما هي | المنفّذ |
| الكميات (2.500 لوح) تتأثر؟ | **لأ.** الكمية مش فلوس — `QuantityCast` ×1000 يفضل زي ما هو | المستخدم (صريح: «في الفلوس») |

**قواعد أعمال حالية بتتأثر:** `CLAUDE.md` قاعدة 1 و2 · `docs/business-rules.md` · `docs/inventory-costing.md` · `docs/system-overview.md` · `docs/cashbox.md` · `docs/partners.md` · `start-agent/PITFALLS.md` (بند 4 و6) · `start-agent/PROJECT.md`

**خارج النطاق صراحة:**
- الكميات (`QuantityCast` ×1000) — تفضل بـ3 خانات عشرية.
- نسب الشركاء (`percentage` ×100) — تفضل زي ما هي.
- أي تغيير في منطق الربح أو الخزنة أو FIFO — الأرقام هي هي، بس بوحدة أكبر.

## 3. الخطة التفصيلية

### 3.1 قاعدة البيانات

**migration واحدة:** `2026_10_08_XXXXXX_convert_money_columns_to_whole_pounds.php`

تمشي على 31 عمود في 14 جدول وتقسم على 100 بتقريب نصف-لأعلى على القيمة المطلقة (آمن للسالب):

```sql
UPDATE `{table}`
SET `{col}` = (CASE WHEN `{col}` < 0 THEN -1 ELSE 1 END) * ((ABS(`{col}`) + 50) / 100)
WHERE `{col}` IS NOT NULL;
```

> على البيانات الحالية ده عملية قسمة نظيفة بلا تقريب (اتأكدنا: صفر قيم فيها كسور). التقريب موجود كأمان لو اتضافت بيانات قبل تشغيل الـmigration.

| `materials` | `unit_price` |
| `inventory_movements` | `cost` |
| `rooms` | `sale_price`, `estimated_materials`, `estimated_accessories`, `estimated_labor`, `estimated_other` |
| `room_materials` | `cost` |

الـ`down()` بيضرب ×100 (رجوع بلا خسارة بعد التحويل).

> ⚠️ **قبل تشغيل الـmigration: ناخد نسخة احتياطية.** صفحة «النسخ الاحتياطي» في النظام بتقول حاليًا «لسه ماتاخدتش» — دي أول خطوة في التنفيذ.

**مفيش أي تغيير في نوع أي عمود** — كلها `integer` قبل وبعد. اللي بيتغير هو **معنى** الرقم: كان قرش، بقى جنيه.

### 3.2 المنطق (Casts / Services)

**(أ) `MoneyCast` — سطرين:**
```php
protected static function scale(): int    { return 1; }   // كان 100
protected static function decimals(): int { return 0; }   // كان 2
```

**(ب) `ScaledIntegerCast` — 3 حراس لحالة `decimals() === 0`** (الكلاس دلوقتي بيفترض إن فيه كسور دايمًا، ومن غير الحراس دي بيكسر):

| الدالة | المشكلة لو decimals=0 | الحل |
|---|---|---|
| `validationPattern()` | بينتج `/^\d+(\.\d{1,0})?$/` — **quantifier غير صالح** | `return '/^\d+$/';` |
| `toDecimalString()` | بينتج `"7000.0"` (نقطة زايدة) | ترجع `"7000"` |
| `toDisplayString()` | `explode('.')` بترجع عنصر واحد → **undefined index** | تتعامل مع غياب الكسر |

`toScaledInt()` **مش محتاجة تعديل** — اتفحصت: بـdecimals=0 بتقرأ `"7000"` → 7000 صح، و`"7000.6"` → 7001 (تقريب نصف-لأعلى) كشبكة أمان لو وصلها رقم عشري من غير المسار الطبيعي.

**(ج) `InventoryService::cost()` — بلا تعديل في الكود، بس معناها بيتغير:**
```
التكلفة (بالجنيه) = round(الكمية_المخزّنة × سعر_الوحدة_بالجنيه / 1000)
```
لسه بتطلع integer بالجنيه. القاعدة رقم 2 في `CLAUDE.md` تتحدّث نصًّا (القسمة على 1000 **بتفضل** لأن الكمية لسه ×1000).

**(د) `InventoryService::unitPriceOf()` و`PartnerService::shareOf()` — بلا تعديل** في الكود، نفس المنطق بوحدة أكبر.

**أثر جانبي واحد لازم يتقال:** التقريب بقى بالجنيه بدل القرش، يعني:
- صرف 2.5 لوح سعره 7 ج.م = 17.5 → **18 ج.م**.
- الحارس الموجود «التكلفة بتقرّب لصفر» هيشتغل في حالات أكتر: شراء 0.1 من خامة سعرها 3 ج.م = 0.3 → 0 → بيترفض برسالة واضحة (مش هيدخل صفر للخزنة).
- نصيب شريك: فرق التقريب بين مجموع الأنصبة والربح القابل للتوزيع بقى لحد جنيه لكل شريك بدل قرش. (نفس السلوك الموجود، بوحدة أكبر.)

### 3.3 التحقق (Form Requests)

**مفيش تعديل في أي من الـ18 ملف** — كلهم بيقرأوا `MoneyCast::validationPattern()`، وتغييره مركزيًا بيخليهم كلهم يرفضوا أي إدخال فيه نقطة عشرية.

**بس** الرسايل العربية لازم تتظبط: `lang/ar.json` / رسالة `regex` الحالية بتقول «صيغة حقل المبلغ غير صحيحة.» — تفضل مفهومة، بس هنضيف رسالة أوضح لحقول الفلوس: **«المبلغ لازم يكون رقم صحيح بالجنيه، من غير كسور.»**

### 3.4 الواجهة

| التغيير | العدد | التفاصيل |
|---|---|---|
| `step="0.01"` → `step="1"` | ~20 حقل فلوس | حقول الكميات `step="0.001"` **ما تتلمسش** |
| `<x-money>` | بلا تعديل في المنطق | بيمر على `toDisplayString()` فبيطلع `7,000` تلقائيًا. التعليق جواه بس يتحدّث |
| `inventory/materials/_fields.blade.php` | قيمة مبدئية | `toDecimalString()` هترجع `"7000"` بدل `"7000.00"` تلقائيًا |
| تصدير CSV | بلا تعديل في المنطق | بيمر على `MoneyCast::toDecimalString()` فبيطلع رقم صحيح تلقائيًا |

**مفيش تعديل في أي Controller ولا Route ولا Service.**

### 3.5 الاختبارات

**(أ) الاختبارات الحالية — 634 اختبار.** الأرقام فيها مكتوبة بالقروش (`3_000_000` = 30,000 ج.م، و`'30000.00'` كنص إدخال). كلها لازم تتحوّل:
- `3_000_000` → `30_000`
- `'30000.00'` → `'30000'`
- أي `assertSeeText('85,000.00 ج.م')` → `'85,000 ج.م'`

العدد: ~107 نص عشري + مئات الأرقام المكتوبة بالقروش موزّعة على 17 ملف اختبار. **ده أكبر جزء ميكانيكي في التاسك** وهيتعمل ملف ملف مع تشغيل الاختبارات بعد كل ملف.

**(ب) ملف جديد `tests/Feature/MoneyIsWholePoundsTest.php`** — ده اللي «بيثبّت» القاعدة ويمنع رجوعها:

| الاختبار | المتوقع |
|---|---|
| نمط التحقق بيرفض الكسور | `MoneyCast::validationPattern()` بيرفض `"10.5"` و`"10.50"` و`"10.00"` ويقبل `"10"` |
| العرض مافيهوش نقطة أبدًا | `toDisplayString()` لعيّنة قيم (0، 7000، -8727، 1234567) مافيهاش `.` |
| `toDecimalString` رقم صحيح | نفس العيّنة بترجع رقم صحيح بلا نقطة |
| كل مسار بيقبل فلوس بيرفض الكسور | POST بمبلغ `"100.50"` على مسارات الفلوس (دفعة عميل، مصروف، تكلفة غرفة، سحب شريك، دَين، رأس مال، شراء خامة، سعر غرفة) → خطأ validation، ومفيش صف اتكتب |
| كل عمود فلوس في الداتابيز بيفضل integer | بعد دورة كاملة (شراء → صرف → تكلفة → دفعة → مصروف → سحب)، كل القيم المخزّنة في الـ31 عمود `=== (int)` القيمة نفسها |
| الـmigration بتحوّل صح | قيمة محفوظة بالقروش قبل الترحيل بتبقى جنيه بعده |

**(ج) `FullCycleIntegrationTest`** — الدورة الكاملة بأرقام جديدة، وده الإثبات النهائي إن الخزنة والربح متسقين بعد التغيير.
