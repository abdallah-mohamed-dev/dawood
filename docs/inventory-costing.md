# تكلفة المخزون — Batch Costing وFIFO

## لماذا Batch لكل عملية شراء؟

كل عملية شراء تنشئ **دفعة (Batch) مستقلة**، حتى لو كانت بنفس السعر ونفس المادة كدفعة سابقة. لا يوجد دمج بين الدفعات أبدًا. السبب: سعر الشراء يتغير بمرور الوقت، ولازم نعرف بالضبط أي كمية خرجت من أي دفعة وبأي سعر، لحساب تكلفة دقيقة لكل غرفة.

## الدفعة (InventoryBatch)

| الحقل | النوع | ملاحظات |
|---|---|---|
| `material_id` | FK | |
| `quantity` | كمية (×1000) | الكمية الأصلية — **لا تتغير أبدًا بعد الإنشاء** |
| `remaining_quantity` | كمية (×1000) | المتبقي — يتناقص بالصرف، يزيد بالإرجاع |
| `unit_cost` | مبلغ (قروش) | سعر الوحدة الواحدة الكاملة وقت الشراء |
| `purchase_date` | تاريخ | يحدد ترتيب FIFO |

**قاعدة:** الدفعة **لا تُحذف أبدًا** بعد نفادها (`remaining_quantity = 0`) — تبقى للتتبع التاريخي والتدقيق. الحذف مسموح فقط للدفعة التي لم يُصرف منها أي شيء (`remaining_quantity == quantity`)، راجع `business-rules.md` §4.

## حركة المخزون (InventoryMovement)

| الحقل | النوع | ملاحظات |
|---|---|---|
| `material_id` | FK | |
| `batch_id` | FK | الدفعة المتأثرة |
| `type` | enum | `in` (شراء) / `out` (صرف) / `return` (إرجاع بعد حذف غرفة) |
| `quantity` | كمية (×1000) | دائمًا موجبة |
| `cost` | مبلغ (قروش) | التكلفة الفعلية لهذه الحركة تحديدًا |
| `related_type` / `related_id` | polymorphic nullable | `null` لحركات الشراء، مرتبط بـ`RoomMaterial` عند الصرف |

## خوارزمية FIFO عند الصرف

عند طلب صرف كمية معينة من مادة:

1. تُجلب كل الدفعات ذات `remaining_quantity > 0` للمادة، مرتبة `purchase_date ASC` ثم `id ASC` (لفض التعادل بين دفعتين بنفس التاريخ).
2. تُخصَّص الكمية المطلوبة من الأقدم للأحدث، دفعة فدفعة، حتى تُغطى الكمية بالكامل.
3. إن كان مجموع المتاح عبر كل الدفعات أقل من المطلوب → **العملية بالكامل تُرفض**، لا تخصيص جزئي (راجع `business-rules.md` §3).
4. كل تخصيص من دفعة يُنشئ حركة `out` مستقلة بتكلفتها الخاصة (كمية × سعر تلك الدفعة تحديدًا).
5. `remaining_quantity` لكل دفعة مُستخدمة يُخصم بمقدار ما أُخذ منها.

### مثال مرجعي كامل

```text
Batch A: quantity = 3 لوح، unit_cost = 100 ج.م، purchase_date = يوم 1
Batch B: quantity = 10 لوح، unit_cost = 120 ج.م، purchase_date = يوم 2

currentStock = 3 + 10 = 13 لوح

طلب صرف 5 ألواح:
  - من Batch A: تؤخذ 3 (كل المتاح) → 3 × 100 = 300 ج.م → Batch A.remaining = 0
  - من Batch B: تؤخذ 2 (الباقي من الـ5) → 2 × 120 = 240 ج.م → Batch B.remaining = 8

إجمالي تكلفة الصرف = 300 + 240 = 540 ج.م
currentStock بعد الصرف = 0 + 8 = 8 لوح

Batch A تبقى في قاعدة البيانات بـ remaining_quantity = 0 (لا تُحذف).
```

## قاعدة التقريب (Round Half Up)

عند ضرب كمية كسرية × سعر وحدة، تُقرَّب النتيجة لأقرب قرش صحيح بطريقة **round half up** (0.5 فأكثر تُقرَّب لأعلى). تُنفَّذ هذه القاعدة في دالة واحدة مشتركة داخل `InventoryService` ولا تتكرر في أي مكان آخر.

## ⚠️ تنبيه: الضرب بين نطاقين مختلفين

الكمية مُخزَّنة **×1000** والمبلغ مُخزَّن **×100**. أي ضرب مباشر بين الكميتين الخام (Scaled) يعطي رقمًا أكبر بـ1000 مرة من الصحيح ما لم يُقسَّم على 1000:

```text
التكلفة (بالقروش) = round( (الكمية_المخزَّنة × سعر_الوحدة_بالقروش) / 1000 )
```

**مثال تحقق:** صرف كمية مخزَّنة `3000` (= 3 ألواح) × سعر وحدة `10000` قرش (= 100 ج.م) ÷ 1000 = `30000` قرش = 300 ج.م. ✅ مطابق للمثال المرجعي أعلاه.

نفس المبدأ يتكرر في حساب نصيب الشريك (نطاق ثالث مختلف — النسبة المئوية)، موثق في `partners.md`.

## الإرجاع بعد حذف غرفة (Return)

عند حذف غرفة صُرفت لها خامات واختيار "إرجاع" (راجع `customers-and-rooms.md`)، تُرجَّع كل كمية إلى **نفس الدفعة** التي صُرفت منها أصلًا (وليس لدفعة جديدة أو لأقدم دفعة متاحة)، بنفس تكلفة الوحدة الأصلية. هذا يحافظ على دقة `remaining_quantity` لكل دفعة تحديدًا.
